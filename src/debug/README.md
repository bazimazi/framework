# src/debug

The debug and agent interface (SPEC §11). So far: reflection of the game state block (task 1A-30), the control protocol (task 1A-31), screenshots (task 1A-32), replays (task 1A-33), snapshots and hashing (task 1A-34), crash dumps (task 1A-35) and the profiler, memory report and log (task 1A-36). Compiled into every runtime and test build, but reached only when `BMF_PROTOCOL_ENABLED` (debug builds and release builds with `BMF_AGENT=1`), except the field-table validation (`bmf_reflect_check_fields`) and the warn/error log counts; a plain release build refuses `--control` and `--replay`.

## Files
- `reflect.h`, `reflect.c`: field-table validation (`bmf_reflect_check_fields`, used by `bmf_core_check_game`), `bmf_fields_hash`, `bmf_field_type_size` (public in `bmf.h`) / `_align` / `_name`, and reflection over a state block (`bmf_reflect`): `bmf_reflect_resolve`, `_live_count`, `_get`, `_set`, `_dump`, `_find_nonfinite`, `_suggest`, `_status_code`. `bmf_core_reflect()` (core) gives the running game's `bmf_reflect`.
- `protocol.h`, `protocol.c`: the stdin reader thread and its line queue, the tokenizer, the dispatch table (`PROTOCOL_COMMANDS`: name, argument count range, handler, usage, owning task for commands not implemented yet), input holds, watches, the closed error-code set (`bmf_protocol_error`). Entry points for the engine: `bmf_protocol_start`, `_poll`, `_after_tick`, `_running`, `_end`; for tests: `bmf_protocol_begin` (with an output callback) and `bmf_protocol_execute`.

- `shot.h`, `shot.c`: `bmf_shot_save` (render with `bmf_core_capture`, encode with `bmf_png_write`, write atomically; pixel and PNG memory borrowed from the permanent arena with mark/pop) and `bmf_image_diff` (per-channel tolerance, differing count and fraction, max channel difference, first differing pixel, optional diff image: differing pixels red, the rest gray at a third of the luma).

- `replay.h`, `replay.c`: the `.bmfr` format (header, RLE start state, record stream of XOR-delta inputs and state writes, checkpoints with state and per-field hashes), the RLE codec, two recorders (session, always on from `bmf_core_start`; explicit, `record start/stop`) and the player (`--replay`, `--replay --verify`, protocol `replay`) with checkpoint verification and the mismatch report.

- `snap.h`, `snap.c`: the protocol's `hash` (`bmf_snap_hash`: NaN/Inf scan, then `bmf_core_state_hash`) and `snap save/load` (`bmf_snap_save`, `_load`, `_clear`): 16 named slots holding a copy of the state block and the tick.

- `crash.h`, `crash.c`: crash dumps: the platform crash hook (registered by `bmf_core_start`) writes `<exe dir>/crash/<UTC>-<game>.bmfr` (`bmf_replay_write_crash`) and `.state` (`bmf_state_file_header` + the state at the session's last checkpoint) and adds `tick`, `phase`, `replay`, `state` (or `dump_error`) to the crash line.

- `profile.h`, `profile.c`: zones (`bmf_profile_zone_begin/end` behind bmf.h's `bmf_zone_begin/end`), a ring of the last 1024 call durations per zone and of frame durations, the `profile` report, the counter calibration, the `mem` report (`bmf_profile_write_mem`, with `bmf_replay_arenas` and `bmf_snap_arenas`).
- `log.c`: `bmf_log_va`/`bmf_log_count` behind bmf.h's `bmf_log`: a 256-message ring with a spin lock, counts per level, a dropped count, the stderr echo, `bmf_log_drain` for `log`.

## Invariants
- The field table is the only description of the state block: names 1..63 bytes of `a-z A-Z 0-9 _ .`, unique, not `tick`; offsets inside the block and aligned to the scalar component (I64/U64/RNG 8, U8 1, others 4); `count_field` only on arrays, naming an I32 scalar anywhere in the table.
- `bmf_fields_hash`: `bmf_hasher` (seed "bmf_fiel") over the field count, then per field in table order the name with its NUL, type, offset and count as little-endian u32. Not `count_field`. 0 only for an empty table. Pinned by `reflect.fields_hash`; any change to the hash breaks every game's declared `state_layout_hash` and needs the owner.
- Debug builds refuse a game whose `state_layout_hash` differs from `bmf_fields_hash` (startup and hot reload), and the message gives the value to declare. Release builds do not compute it.
- Paths: `name`, `name[i]`, `name[*]`; exact, case-sensitive names; indices are plain decimal (no sign), bounded by the live count (`count_field` value clamped to 0..count). `name` on an array means every live element. Built-in path `tick` (read-only, ticks completed).
- `set` writes exactly one element, parses and checks every value before writing (a failed set changes nothing), refuses NaN/Inf (D-37 rule 11), keeps a count field within the capacity of every array it counts and an RNG's inc odd.
- The NaN/Inf scan covers every element of every F32/V2/V3/V4 field up to its full count (dead elements are state and are hashed).
- No allocation; output goes to a caller's `bmf_json_writer`, details to a caller's buffer. Main thread, between ticks.
- Protocol: exactly one response line per request, in request order; events a request causes (watch changes during `step`) are written before its response; empty and `#` lines get none. A failed request writes nothing but its error response (the half-built response is dropped). Every response line is flushed at once.
- `--control` starts paused; time advances only by `step` (synchronously, inside the request) or while `run` is in effect (real time). `press`/`axis` inject at once (the next tick samples them) and are released by the tick hook after TICKS ticks, so `press X 1` gives pressed on the next tick and released on the one after.
- Watches are re-resolved after every tick (paths survive reloads and live-count changes) and report when the hash of their value text, or their error code, changes.
- The reader thread is the only producer and the main thread the only consumer of the 64-line queue (`written`/`read` counters, futex waits on both). End of stdin requests quit. The reader is never joined: it blocks in `ReadFile` until the process exits.

- A shot never changes the state or the clock and never presents; repeated shots of one state are byte-identical on one backend. Images differ slightly between backends (hardware vs WARP: 1 pixel off by 1 in a 1280x720 `_loop` shot), so goldens are per backend (A-08).

- Replays: input record k is the input sampled for tick start_tick + k; state records sit between the input records they were written between and are applied just before the next input (after the previous tick's checkpoint). Checkpoints are taken after a tick: at the start, every 60 ticks after it and at the end. A replay is valid for the game build that recorded it (same name, state size, layout hash, field count, tick rate); a different build id only warns, so golden replays can check that a new build is still deterministic. Protocol `set` is recorded as a state write, so protocol sessions replay exactly. Anything that replaces the state and tick between ticks (hot reload, `snap load`, protocol `replay`) restarts the session recording from the new state, breaks an explicit recording and stops a playing replay (`bmf_replay_on_state_replaced`); an input record therefore always belongs to tick start_tick + k.
- Hashing: `hash` never hashes a state with NaN/Inf in a reflected float: it answers `nonfinite_state` with the first such path. Every other hash pass (`bmf_core_state_hash`: replay checkpoints, verification) asserts on it in debug builds (D-37 rule 11), so a NaN stops a debug game at the next checkpoint at the latest (60 ticks).
- Crash dumps: the crash replay covers the session recording from its start to start_tick + input records, which after a crash inside a tick includes that tick's input (it is recorded before the game's tick runs), and it has no final checkpoint (the state may be half-way through a tick; hashing it could assert). Replaying it with `--replay` runs into the same crash at the same tick. The `.state` is the copy the session recorder keeps of the state at its last checkpoint (taken after that checkpoint's hash pass passed). Crash-time code uses only static buffers, the recorder's arenas and stack (atomic writes from parts: nothing is assembled). Only debug and `BMF_AGENT` builds have dumps (the session recording); plain release builds print the crash line only.
- Profiler: zones are main thread only and must nest; the engine's tick zone closes around the game's tick, so a zone the game leaves open is a nesting error at the end of that tick. Debug builds assert on a nesting error with both zone names; release builds with `BMF_AGENT` count it and close the zones opened inside the one being closed. Timestamps are rdtsc on x64; their frequency is measured against `bmf_platform_time_ns` over the whole time since `bmf_core_start` (at least 10 ms: the first report may wait). Stats per zone are per call: calls in the window, mean over all of them, p50/p99 (nearest rank) over the last 1024, max over all. `profile N` (N > 0) starts a window, runs N ticks, reports and starts the next window; `profile 0` reports the window since the last report. `game.exe --replay F --profile` prints the same report for the whole replay run (one tick and one draw per frame) when it ends (perf budgets, task 1A-42). Profiling never touches the state.
- Log: messages are text up to 255 bytes, stamped with the ticks completed (-1 with no game running); a full ring drops its oldest message and counts it; `log` drains everything and returns the messages of at least the requested level. Counts per level run from `bmf_core_start`. Only the main thread echoes to stderr (the runtime turns the echo on in `--control` mode). Release builds without `BMF_AGENT` compile `bmf_log` to a count of warn and error messages.
- Snapshots: a slot holds the state block and tick only (not input holds, watches or the GPU view). Saving an existing name overwrites it. A slot remembers the state size and layout hash and is dropped when loaded into a game with another layout. `bmf_core_start` clears every slot.

## Data layout
`bmf_reflect` is five words that point at engine-owned data (field table, state block, tick counter); it holds no state of its own and lives outside the state block. Protocol: one static struct (holds per action, 32 watches of path + last hash) plus static buffers: the line queue (64 x 4 KiB), a 1 MiB response line, 64 KiB each for event lines and watched values. Profiler: static, 64 zones x 1024 u64 samples (512 KiB) plus 1024 frame samples and the sort buffers. Log: static, 256 x 272-byte entries (68 KiB). Crash: static path buffers; the session recorder reserves one more state-sized range for its last-checkpoint copy. Snapshots: 16 static slot records; each slot reserves 1 GiB of address space (the state limit) on its first save and commits the state size. Replay: each recorder reserves address space for its start state (up to the 1 GiB state limit), 256 MiB of records, 64 MiB of checkpoints (and the session recorder its last-checkpoint state; files are written from these parts, never assembled); the player maps the file and reserves a 1 GiB snapshot range. All committed only as used. Not part of the state block.

## Hot paths
Per tick in debug and agent builds: the session recorder XORs the 224-byte input in 28 u64 words and appends 1 byte (unchanged input) or a short RLE record; every 60 ticks it hashes the state and each field. Measured on `_loop` (debug, no GPU, 3 M ticks): 0.27 us/tick without the recorder, 0.51 us/tick with it (0.23 us/tick of recording). The checkpoint hash includes the NaN/Inf scan in debug builds (O(reflected float bytes), every 60 ticks: no measurable change, `_loop` 3 M ticks 1368..1430 ms after vs 1517 ms before), and the session recorder copies the state block at each checkpoint (1A-35: `_loop` 1367..1499 ms, no measurable change). Zones (1A-36): the engine opens three zone pairs per tick in debug and agent builds (tick, and debug_hooks twice), about 10 ns per pair in a debug build (`_loop` 3 M ticks 1568..1716 ms vs 1367..1499 ms; `profile 1000` on `_loop`: tick 0.027 us, debug_hooks 0.20 us p50). Everything else runs at protocol rate: lookups are O(fields) by name, suggestions O(fields x 63^2), `hash`/`snap` O(state).

## Limits
- Up to `BMF_FIELD_MAX_COUNT` (4096) fields. Count fields are found by name on every access (no index cache).
- Built-in engine paths: `tick` now, `phys.*` when physics (M6) lands. An RNG in the state is reflected through a `BMF_T_RNG` field as `[state, inc]` (see the 1A-30 note in PLAN.md).
- Protocol: `help` lists every command with its usage; a leading UTF-8 BOM on a line is skipped (PowerShell 5.1 pipes one). Requests up to 4095 bytes and 16 tokens, responses up to 1 MiB (`response_too_large` beyond: use `dump PREFIX`), 32 watches. `--control` with a window keeps rendering at vsync while paused. `phys` answers `not_implemented` until 1B-09 (`phys query`; `phys draw` is 1B-11).
- Profiler: 64 zones (engine 0..4, game 32..63), 32 open at once, stats over the last 1024 calls per zone and 1024 frames. Log: 256 messages of 255 bytes.
- Snapshots: 16 names of 1..31 characters (`A-Z a-z 0-9 _ . -`); `too_many_snaps` for a 17th.
- Shots: up to 8192 x 8192, if pixels plus PNG fit in the free part of the permanent arena (64 MiB default: about 2900 x 2900); stored deflate makes files about as big as the raw pixels (3.7 MB at 1280x720). About 29 ms per 1280x720 shot in a debug build on WARP (render, readback, encode, write).
- Replays: about 1 byte per tick of unchanged input plus 16 + 8 x fields bytes per checkpoint (`_loop`, 3600 ticks: 6781 bytes). The mismatch report lists at most 16 fields and leaves out values over 16 KiB of JSON. The first diverging tick is known to checkpoint precision (60 ticks).
