# src/input

Actions, bindings and per-tick input sampling (SPEC §10, D-24, task 1A-22). The simulation never sees devices, only the fixed-size POD `bmf_input` that the engine samples once per tick from this module.

## Files
- `../bmf.h` (public, sections "Keys" and "Input"): `bmf_key`, action types, binding values, `bmf_action`, `bmf_pointer`, `bmf_input` (224 bytes, no implicit padding), the bit helpers `bmf_input_down/pressed/released` and the run-time action calls (`bmf_input_set_pointer_camera`, `_action_find`, `_action_type`, `_action_slot`, `_bind`, `_binding`, `_reset_bindings`).
- `input.h`: the engine side: the engine interface (`bmf_input_init`, `_check_actions` (the same rules without touching input state; the engine checks a reloaded game with it), `_set_view`, `_event`, `_set_gamepads`, `_sample_tick`, `_text_dropped`) and the injection calls for the control protocol (`bmf_input_inject_button`, `_axis`, `_pointer`). Every function has its contract comment.
- `input.c`: validation, bindings, device state, edge sampling, pointers, text queue. Included by `bmf.c` after draw2d (it uses `bmf_camera` for pointer mapping).

## Invariants
- The module never calls the platform. The engine (1A-23) pumps `bmf_platform_event_pop` into `bmf_input_event` and `bmf_platform_gamepad_get` into `bmf_input_set_gamepads` once per frame, then calls `bmf_input_sample_tick` once per tick. The protocol (1A-31) feeds raw keys as `bmf_event`s through the same call, so agents and tests run the player's code path.
- Action table: names unique, 1..31 bytes of `a-z A-Z 0-9 _ . -` (protocol tokens); at most 64 BUTTON, 8 AXIS2 and 1 POINTER actions. BUTTON actions get bits 0, 1, ... and AXIS2 actions axes 0, 1, ... in table order, counting each type separately. A failed `bmf_input_init` returns `BMF_ERR_INVALID` with a one-line message naming the action, and leaves an empty table.
- Binding values (u16): a source in bits 0..11 (bmf_key values 1..`BMF_KEY_COUNT` - 1, i.e. 1..117, `BMF_MOUSE_*` 0x100.., `BMF_PAD_*` buttons 0x200.. in `bmf_gamepad_button` bit order plus the two triggers, the two-dimensional `BMF_KEYS_WASD/ARROWS`, `BMF_PAD_LSTICK/RSTICK/DPAD` 0x300..) and, for AXIS2 only, a direction in bits 12..14 (`BMF_AXIS_UP/DOWN/LEFT/RIGHT`) on a digital source. BUTTON takes digital sources without direction; AXIS2 takes two-dimensional sources or digital ones with a direction; POINTER takes none. Init and `bmf_input_bind` check the same rule.
- Buttons: an action's level is "any binding source down, or injected". Every rise of the level is counted (`press_count`, at most 15 waiting). Per tick (`input_edge_step`): if the previous tick was down and a press is waiting, this tick is up (the release in between is shown); else if a press is waiting, this tick is down and the press is used; else the tick follows the level. `pressed`/`released` compare with the previous tick. So a press shorter than a frame is down and pressed on exactly one tick, frames of 0 ticks lose nothing, and two taps in one frame give two presses. Key auto-repeat is ignored.
- Axes: no edges and no latch, sampled from the current state each tick. The sum of all bindings (direction keys and D-pad as unit vectors, sticks as given) is scaled to length 1 when longer (real `sqrt` and division, so diagonals are exactly 1/sqrt(2) = 0x3F3504F3). +x right, +y up. An injected value replaces the bindings and is normalized the same way.
- Gamepads: buttons of every connected pad are OR'ed; each stick binding uses the pad whose stick is pushed furthest (lowest index on a tie); triggers count as down at `BMF_INPUT_TRIGGER_DOWN` (0.5). A disconnected pad releases everything it held.
- Pointers (only with a POINTER action; otherwise `pointer[]` stays zero): slot 0 is the mouse (id 1, down = left button) and the primary touch. A touch/pen contact takes the lowest free slot, preferring slots whose last contact has been fully reported; slot 0 counts as free while the mouse button is up. Contacts get ids 2, 3, ... in order (injected pointers draw from the same counter); more than 4 are ignored. A finished contact keeps its id until its release has been sampled, then the slot reads id 0; the mouse takes slot 0 back on its next move or left-button event. A release forced by focus loss carries (0, 0), so the position of a POINTER_UP is not used. Positions: event pixels / view DPI scale = logical pixels; `world` = `bmf_camera_screen_to_world(pointer camera, logical view size, screen)` at sample time (default world camera; games set theirs with `bmf_input_set_pointer_camera`).
- Injection: `inject_button` is a level OR'ed into the action (same press counting); `inject_axis` replaces the value while active; `inject_pointer` takes a slot over (a touch there is released, its later events ignored) until an UP, converting camera-space positions to logical pixels at once.
- Text: a 64-codepoint queue; each tick takes up to 8, the rest wait. Overflow drops the newest (`bmf_input_text_dropped`).
- Sampling is presentation-side (device order), but its output is what replays store, so ticks stay deterministic whatever the devices did.

## Data layout
One static `input` struct (about 2.5 KiB): the table pointer and per-type index maps, the bindings in use (`[73][8]` u16), view and pointer camera, device state (keys as two u64 bitsets, mouse button bits, combined pad button bits, two stick vectors, mouse position), per-button level/injection/previous bits as u64 with a u8 press count per bit, axis injections, 4 pointer slots (owner, touch source, id, position, level, press count, previous down) and the text queue. No heap, no arena.

## Hot paths
None. Per event: O(button actions x bindings) for keys and mouse buttons (at most 64 x 8 checks), O(1) otherwise. Per tick: the same loop for buttons plus axes x bindings, 4 pointer slots and a text copy. Not measured: a frame handles a handful of events and up to 4 ticks.

## Limits
- Hot reload: the engine keeps its own copy of the action table (so input never points into an unloaded DLL) and calls `bmf_input_init` again only when the reloaded table differs; that resets rebinding and held state.
- No per-player gamepad assignment (every pad drives every pad binding), no 1D trigger axis, no mouse wheel or raw mouse delta in `bmf_input`, no rebinding capture ("press the key you want"), no binding names for settings files. Axis taps shorter than a frame do not move the axis.
- `-Wextra` (the game build flags) requires the bindings field in every table entry: write `{ "aim", BMF_ACTION_POINTER, { 0 } }` rather than SPEC §10's `{ "aim", BMF_ACTION_POINTER }`.

## Tests
`tests/test_input.c`: validation (every rule, message text, 64/8 limits, empty table on failure), edges across frames of 0, 1 and 4 ticks, presses shorter than a frame (single, double tap, re-press while held, saturation at 15, mouse button), axis normalization (diagonals, cancelling keys, sticks inside and beyond the unit circle, key plus stick, furthest stick, direction keys, injection), bindings (rebind, errors, clear, reset, any pad, trigger threshold, disconnect, D-pad), pointers (DPI, world mapping with three cameras, mouse and touch slots, more contacts than slots, release then id 0, touch tap, no POINTER action), injection (held press, with a key, one-tick press, world-space pointer, takeover, raw key by name), text (8 per tick, overflow).
