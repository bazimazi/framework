# tools/test

The unit-test runner, the golden runner and the perf budget runner, built and run by `build test [filter] [--update-golden NAME]` (out/test/win64-debug/test.exe).

- Golden tests (task 1A-41, `golden.c`): after the unit tests, `build test` builds every game that has a `tests/` folder (win64 debug) and runs `test.exe --golden [filter]`: the lint, then per game every `tests/*.bmfr` through `game.exe --replay F --verify`, and every `tests/golden/d3d11/*.shot` (sidecar: `replay F`, `tick T`, `size WxH`) by playing the replay to the tick headless on WARP and comparing the shot with the `.png` next to it (a pixel differs when a channel is off by more than 2; at most 0.1% may differ, SPEC §15). A failing image leaves the actual image and a diff image (differing pixels red) in `out/test/golden/`; a failing replay prints the replay's mismatch line (tick, last match, both hashes, the fields that differ). One `{"test":"golden.<game>.<file>",...}` line each, then `{"goldens":N,"passed":P,"failed":F,"ms":T}`. A filter runs the golden phase only when it starts with `golden` or `lint`.
- Scenarios: `games/<g>/tests/<scenario>.script` holds protocol requests; `build test --update-golden <g>.<scenario>` (or `<g>` for all of a game's) records it at the game's own rate and at 120 Hz (once for a 120 Hz game) (D-32: tick counts in `step`/`press`/`axis` are in the game's ticks and are scaled; they must divide evenly) into `<scenario>.<R>hz.bmfr`, and turns each `golden LABEL` line into `golden/d3d11/<scenario>.<R>hz.<LABEL>.png` + `.shot`. `seed N` and `size WxH` (default 320x180) set the run. A script without recordings fails. Every rewritten file is printed as `{"golden":"updated","file":F,"changed":B}` (replays compare without their build id): name each one in the change summary (R5).
- Engine goldens: unit tests that render on WARP call `test_golden_image(t, name, rgba, w, h)`, which compares with `tests/golden/d3d11/<name>.png` (same tolerances; actual and diff in `out/test/golden/`) or rewrites it when `--update-golden` selects the name (`draw2d.shapes`, `draw2d.cameras`, `draw2d.font`; `--update-golden draw2d` selects all three). A name selects goldens equal to it or starting with it plus `.`.
- Lint: `src/physics2d/*.c` and every top-level `.c` file of `games/<g>/` and `tests/bench/<s>/` that contains the text `// bmf-lint: sim` anywhere (subfolders are not scanned) must not use `bmf_fast_*`, `rdtsc`, `__builtin_fma*` or raw float-to-int casts (D-37 rules 4, 1, 9, 12). Comments and string literals are skipped. A cast counts as float-to-int when its operand is a float literal, a parenthesized expression holding one, or a call of a function whose name ends in `f` or `f32` (not `sizeof`/`offsetof`/`typeof`); casts of float variables are not caught (a heuristic, by the task's definition). One `lint.<path>` line per scanned file, listing `path:line: rule` findings.
- Golden PNGs are stored-deflate (no compression until the full inflate of 1B-30): 320x180 is 230 KB.
- Bench scenes (`tests/bench/<scene>/game.c`, task 1A-42) are built and checked like games: their `tests/` goldens (replays, scripts, `--update-golden <scene>.<scenario>`) and the lint marker work the same, and a scene may include the engine's internal headers (games may not). `sprites10k`: 10 000 sprites on 8 layers with 4 textures; `tests/bench.script` (600 ticks, no input) gives `bench.60hz.bmfr` and `bench.120hz.bmfr`.
- Perf budgets (task 1A-42, `perf.c`): after the goldens (not with `--update-golden`), `build test` builds every game and bench scene that has a `perf.budget` with `build win64 release <dir> --agent` (out/<g>/win64-release-agent) and runs `test.exe --perf [filter]`. Budget lines: `replay=<path>` (relative to the game folder, 1..8), `size=WxH` (default 1280x720), `zone=<name> <stat><=<us>` with stat `p99_us`, `p50_us`, `mean_us` or `max_us` (1..32), `#` comments. Each replay runs as `game.exe --headless --no-gpu --replay F --profile --size WxH` (one tick and one draw per frame, as fast as possible); the report covers the whole run (per call: mean, p50/p99 over the last 1024 calls, max). A run over budget is repeated, up to 3 runs, and the replay passes when one run meets every limit: a burst of load from outside (seen once: draw p99 648 us with p50 unchanged, right after the release builds) does not fail it, while a regression fails all three. One line per replay (its last run): `{"test":"perf.<g>.<replay stem>","ok":B,"ms":T,"runs":R,"budgets":[{zone, stat, limit_us, value_us, ok}...],"profile":{...the whole report...},"msg":"draw p99_us 107.45 > 25 (perf.budget line 9)"}` (msg on failure only; a zone that never ran fails its limits), then `{"perf":N,"passed":P,"failed":F,"ms":T}`. A filter runs the perf phase only when it starts with `perf`. Every run is appended to `out/bench/history.jsonl` as `{"time":UTC,"rev":HEAD commit (read from .git, left out when unreadable),"scene","replay","size","ok","profile"}`.
- Why the null GPU backend: the budgets measure the CPU work of the engine and game (SPEC §12.3 counts CPU submit + sort). On WARP the software rasterizer runs inside the flush's buffer map (sprites10k at 320x180: `draw2d_flush` 2.5 ms on WARP vs 0.06 ms on null), and hardware GPUs need a window (none when the session is locked). The ring upload is therefore not in the budgets; a windowed hardware run (Intel UHD 770, session locked so the window was occluded, noisy) gave `draw2d_flush` p50 145 us vs 57 us on null.

- Tests are plain functions `static void test_x(bmf_test* t)` in `tests/test_*.c`, listed by hand in the `TESTS[]` table in `tests/tests.c`. No auto-registration.
- Checks: `bmf_check`, `bmf_check_eq_i64`, `bmf_check_eq_u64` (hex), `bmf_check_eq_mem`. Each takes the call site explicitly: `..., __FILE__, __LINE__, "message")`. A failed check records the first failure and the test continues.
- `bmf_test_note(t, text)` attaches a measurement to the test's line as `"note"` (pass or fail), for example the math tests' max ULP error and output hash.
- Output: one JSON line per test (`{"test":..,"ok":1,"ms":..,"checks":..}` plus `note` when set, and `failures`, `file`, `line`, `msg` on failure), then `{"tests":N,"passed":P,"failed":F,"ms":T}`. Exit code 0 if all passed, else 1.
- Expected-crash tests (third column `1` in the table) run in a child process (`test.exe --run-one NAME`, Windows Error Reporting off) and pass when the child dies with an exception code (`>= 0xC0000000`), reported as `exit_code`. The runner reads the child's output and deletes the crash dump files its crash line names.
- The runner starts with `bmf_platform_init` and uses the platform layer for arguments, time and stdout (`src/platform/platform.h`).
- Output lines are written with `bmf_json_writer` and messages with `bmf_fmt_buf` (`src/base/base_string.h`); use `bmf_fmt_buf` to build check messages and notes.
- `tests/gen/` holds test-only reference code (`math_ref.c`: big-integer and double-double reference for the math tests).
- Known: the test build is debug (-O0 + UBSan); the math ULP tests take about 4 s and the 10M float round trip about 5 s of the run.
- `test.exe --game-child GAME FLAGS...` runs a test game through `bmf_core_run` (`protocol`, defined in `tests/test_protocol.c`, `snap`, in `tests/test_snap.c`, or `crash`, in `tests/test_crash.c`, or `profile`, in `tests/test_profile.c`): process-level tests spawn the runner itself with piped stdin/stdout, so no game exe needs to be built.
- Host check `api` (1A-24): `build test` scans `src/bmf.h` and fails when a function declared or defined at file scope has no comment line directly above it or above its group (no blank line in between); it then copies `bmf.h` alone to `out/gen/api/` and compiles every `games/<name>/game.c` with `-fsyntax-only` and only that folder on the include path, so a game that needs anything besides `bmf.h` fails. It also fails when `API.md` differs from what `build api` (1A-43) generates from `bmf.h` now (`api_md_stale`: run `build api`; line ends ignored; `api_md_missing` without one), when a game needs more than `bmf.h` (`game_needs_more_than_bmf_h`; bench scenes are not compiled this way) or the estimate is over 30 000 tokens (`api_over_token_target`). One `{"host_check":"api",...,"api_md_tokens":N}` line (plus one line per problem).
- `build api` (1A-43, build.c): runs the contract-comment scan, then writes `API.md` at the root from `src/bmf.h` with a line parser over the header's layout: the file comment becomes the introduction, `// ====` banners become `##` sections (listed under Contents), `// ----` lines `###` subsections, a comment block right after a heading that ends at a blank line or heading becomes prose, and everything else (contract comments, declarations, types, constants, macros) stays verbatim in C blocks, except that static inline functions keep only their signature (forward declarations of them are dropped) and the include guard, `#include` and final `#endif` are left out. Also left out of API.md: preprocessor conditional blocks, `BMF_STATIC_ASSERT` lines, declaration groups whose comment starts with `// Engine side`, parenthesized spec/decision/task references; runs of alignment spaces become one. The top line gives the API version, the function count and a token estimate (bytes / 2.07, rounded up: calibrated 2026-11-22 against a real tokenizer count of API.md, 66 461 bytes = 32 133 tokens; the earlier bytes / 3.5 underestimated by 40 %). Nothing is written when a check fails: `{"build":"fail","target":"api","ok":0,"error":"no_contract_comment","file":...,"line":N,"function":F}` or `api_over_token_target`, then the summary line.
- Host checks: before the runner starts, `build test` builds and runs `tests/test_vtable_slots.c` (`out/test/win64-debug/vtable_slots.exe`, rebuilt only when its inputs change). It compares every typed COM method slot, every pinned struct size and the D3D11/DXGI GUIDs of `win32_api.h` with the Windows SDK headers and prints one `{"host_check":"vtable_slots",...}` line (plus one line per mismatch). A mismatch fails `build test` (the unit tests still run); if `vtable_slots.exe` does not compile, `build test` stops before the runner with `vtable_check_compile_failed`. It needs the MSVC C headers (newest Visual Studio `VC\Tools\MSVC\<ver>`, or the `BMF_MSVC` env var); without them it prints `"skipped"` and passes.
- Test shaders: `tests/shaders/d3d11/<name>.hlsl` are compiled by `build test` exactly like the runtime's (task 1A-15) into `out/gen/test_shaders_d3d11.h` (`GPU_TEST_SHADER_<NAME>`, ids 56..63, above every runtime shader id). Tests never compile HLSL at run time; `gpu_d3d11_test_shaders()` (a helper in `tests/test_gpu_d3d11.c`) copies the generated entries into the backend's table.
